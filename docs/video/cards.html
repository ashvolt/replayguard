ReplayGuard

Does your durable workflow charge the card twice when it crashes?

  • Injects crashes, lost responses, timeouts and real process kills around every external call
  • Restarts the workflow like a real host, and classifies every effect
  • Runs on the real Rivet engine — in process, in a killed child process, and on RivetKit actors

The gap: history is written after the step

Durable execution replays your code. It cannot un-send a request.

step "charge" starts→provider charges the card→ process dies→step result never saved→ restart re-runs the step→charged twice
  • Correct, documented at-least-once behaviourThe fix is an idempotency key — if you know you need one, and where.
  • Rare in tests, inevitable in productionCrashes, deploys, timeouts and lost responses all take this path.

How it works

1 · record

Effect ledger

Each external call is wrapped; every attempt, its key, timing and result are recorded.

2 · break

One fault per case

Crash before/after a call, lost request or response, hanging provider, real process kill — explored automatically.

3 · judge

Outcome per effect

Compared with a clean baseline run, with a cause, a verdict and a fix hint.

exactly-onceas in the baseline
deduplicatedreplay recognised
duplicatedapplied more often
concurrent-duplicateoverlapping calls
orphanedapplied, then workflow failed
skippedexpected, never applied

The demo workflow

simplified from examples/checkout-demo · real @rivet-dev/workflows engine · fake providers

await scenario()
  .runtime(workflowsRuntime())
  .effects((ctx) => ({ payment: createFakePayment(ctx), email: createFakeEmail(ctx) }))
  .workflow(({ payment, email }) => async (wf) => {
    await wf.step("charge", () => payment.charge({ orderId: "order-42", amount: 4999 }));
    await wf.step("receipt", () => email.send({ to: "ada@example.com", template: "receipt" }));
  })
  .explore()      // crash / lost response, before / after each call → 8 cases
  .build()
  .run({ classify: true });

Act 2: one line

A key derived from the workflow ID and the step name — the same on every re-execution

await wf.step("charge", () =>
  payment.charge({
    orderId: "order-42",
    amount: 4999,
    idempotencyKey: idempotencyKey(wf, "charge"),   // "<workflowId>:charge"
  }));
  • Never a timestamp, a random value or an attempt numberThey change on every retry; ReplayGuard flags this as unstable-idempotency-key.

Same scenarios, three runtimes

in process

@rivet-dev/workflows

Fault-injecting storage driver; fast enough to explore every fault point.

process kill

Child process + file store

The OS process is killed at the fault; the next run is a new process on the same store.

actors

RivetKit workflow actors

Real engine; host killed with SIGKILL; the actor resumes on a new host from persisted history.

  • One conformance suite, identical outcomes on all threeSix spike scenarios · engine runtimes in CI on Linux, macOS and Windows · actors on Linux with RivetKit 2.3.11 and 2.3.27
